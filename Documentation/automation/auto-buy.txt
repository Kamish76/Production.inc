
Auto-Buy Machine — Specification
=================================

Purpose
-------
Provide a simple, predictable automation that periodically purchases raw materials for the player. NOTE: the configured "cap" described below is not a hard inventory maximum — the player's inventory is effectively unlimited. The cap describes the machines' per-item target/capability (how much the machines will aim to regulate per item), and it multiplies with additional machines. Machines should use their full per-tick purchase capacity so ticks are not wasted.

Summary of behavior
-------------------
- Players may own one or more Auto-Buy Machines. Machines are stackable and identical in base behavior.
- Machines can be toggled On/Off as a group by the player in the Buy screen. When toggled Off, all auto-buy machines stop purchasing completely until re-enabled.
- Machines operate on a global tick that runs every 10 seconds (configurable). On each tick, enabled machines purchase materials up to the configured caps and throughput.

Configurable parameters (default values)
----------------------------------------
- buysPerMachinePerTick: 5 — the number of items one machine attempts to buy per tick (default 5).
- baseLimitPerItem: 5 — the per-item cap contributed by a single machine (default 5).
- tickIntervalSeconds: 10 — global tick frequency in seconds (default 10).
- resourceOrder: deterministic list/order of resources to service each tick (see selection rules).

Algorithm (pooled-capacity buying rules)
-----------------------------------------
This section explains the deterministic algorithm used by all enabled Auto-Buy Machines on every global tick. All enabled machines pool their buying capacity and apply it as a single batch per tick.

Contract (inputs/outputs)
- Inputs: current inventory map (resource -> amount), machinesEnabled (int), buysPerMachinePerTick (int), resourceOrder (ordered list), resourceCap (per-resource cap for machines to aim for)
- Outputs: updated inventory map after consuming all pooled buys
- Error modes: negative inputs are clamped to zero; purchases cannot reduce inventory below zero; any fractional buys are rounded down to integer counts.

High-level rules
- Total pooled buying capacity per tick = machinesEnabled × buysPerMachinePerTick
  - Example: 2 machines × 5 buys/machine/tick = 10 total buys per tick
  - Example: 3 machines × 5 buys/machine/tick = 15 total buys per tick
- On each tick, the system processes resources in the configured `resourceOrder` sequentially, using the pooled buying capacity.
- For each resource in order:
  - Calculate deficit = max(0, resourceCap - currentInventory)
  - If deficit > 0 and pooled buys remain:
    - buyAmount = min(pooledBuysRemaining, deficit)
    - Add buyAmount to inventory
    - Subtract buyAmount from pooledBuysRemaining
  - If deficit = 0 (resource at or above cap), skip to next resource
- After processing all resources in resourceOrder once, if pooled buys remain, wrap back to the top and repeat until pooledBuysRemaining = 0 or all resources are at-or-above resourceCap.

Edge cases and notes
- If pooled buys remain after a full pass through resourceOrder but all resources are at-or-above resourceCap, the remaining buys are unused for that tick.
- The `resourceCap` is a soft per-resource target. The system checks it each time before buying.
- This algorithm favors earlier resources in `resourceOrder` (they are filled first). Resources later in the order only receive buys if earlier ones are at cap or the pooled capacity exceeds their deficits.

Example scenario (pooled-capacity model)
-----------------------------------------
Setup / assumptions
- machinesEnabled = 2 (both machines active)
- buysPerMachinePerTick = 5
- Total pooled buys per tick = 2 × 5 = 10
- resourceCap = 10 (per resource)
- resourceOrder = [metal, wood, plastic]
- starting inventory: metal = 3, wood = 10, plastic = 5

Tick-by-tick trace (pooled buying, single batch per tick)
- Tick 1 start: metal = 3, wood = 10, plastic = 5; pooled buys = 10
  - Process metal: deficit = 10 - 3 = 7. Buy min(10, 7) = 7 → metal = 10. Pooled buys remaining = 3.
  - Process wood: deficit = 10 - 10 = 0 → skip (already at cap).
  - Process plastic: deficit = 10 - 5 = 5. Buy min(3, 5) = 3 → plastic = 8. Pooled buys remaining = 0.
  - Pooled buys exhausted. Tick 1 ends.

Result after Tick 1: metal = 10, wood = 10, plastic = 8

- Tick 2 start: metal = 10, wood = 10, plastic = 8; pooled buys = 10
  - Process metal: deficit = 0 → skip.
  - Process wood: deficit = 0 → skip.
  - Process plastic: deficit = 10 - 8 = 2. Buy min(10, 2) = 2 → plastic = 10. Pooled buys remaining = 8.
  - All resources at cap. Remaining 8 pooled buys unused. Tick 2 ends.

Result after Tick 2: metal = 10, wood = 10, plastic = 10 (all capped)

This trace uses the pooled-capacity model: all machines' buys are pooled into a single batch per tick and applied in resourceOrder. It's simpler to reason about and implement than the per-machine sequential model.

Scaling examples (pooled capacity with different machine counts)
- 2 machines: 2 × 5 = 10 buys per tick
- 3 machines: 3 × 5 = 15 buys per tick
- 4 machines: 4 × 5 = 20 buys per tick
- N machines: N × 5 = (5N) buys per tick

Development Mode (Temporary)
----------------------------
This feature is currently in development. To facilitate testing and tuning:
- The buy screen will include temporary controls to add/subtract the number of machines owned.
- These controls allow developers to modify the buyer automation behavior dynamically during testing.
- Once the feature is finalized and released, these temporary controls will be removed and machine ownership will follow the normal game progression (purchase, unlock, etc.).
