## 🔧 HOW THE QUEUE SYSTEM IS IMPLEMENTED

The v1.4.10 queue system is implemented with the following key components:

### 📋 DATA MODEL:
- `ProductionTask.isQueued` - Boolean flag to track whether a task is waiting in queue
- `ProductionTask.quantity = 1` - Each task represents a single unit for proper sequential processing
- Individual tasks are created for each unit when building multiple quantities

### ⚙️ QUEUE LOGIC IN `startProduction()`:
```dart
// Check if there's already an active production of this product type
bool hasActiveProduction = existingActiveProductionExists;

// Create individual tasks for each unit
for (int i = 0; i < quantity; i++) {
  // First task: queue only if there's already an active production
  // Subsequent tasks: always queue them  
  bool shouldQueue = hasActiveProduction || i > 0;
  
  // Create task with quantity = 1 for proper queueing
  ProductionTask(
    quantity: 1,
    isQueued: shouldQueue,
    // ... other fields
  );
}
```

### 🔄 QUEUE PROCESSING IN `updateProductions()`:
```dart
for (final task in activeProductions) {
  if (task.isQueued) {
    // Check if this queued task should start now
    final hasActiveProductionOfSameType = activeTasks.any(
      (otherTask) => otherTask.productId == task.productId && !otherTask.isQueued,
    );
    
    if (!hasActiveProductionOfSameType) {
      // Start this queued task
      final startedTask = task.copyWith(isQueued: false, startTime: DateTime.now());
      activeTasks.add(startedTask);
    } else {
      // Keep it queued
      activeTasks.add(task);
    }
  }
  // ... handle other task states
}
```

### 🐛 KNOWN ISSUE:
Despite the correct implementation logic above, user testing on real devices indicates that the queue system is still batching tasks after the first one, rather than processing them strictly one at a time. The implementation should ensure only one task of each product type is active at any given time, with subsequent tasks waiting in queue until the previous task completes.

### 🧪 TEST STATUS:
- Core queue logic tests pass in the test environment
- Build quantity preferences work correctly
- Database persistence of queue state works correctly
- **Issue**: Real device behavior differs from test environment expectations

### 📱 DEVICE TESTING REQUIRED:
Further investigation is needed to understand why the queue system works correctly in tests but may not behave as expected on real devices. This could be related to:
- Timer update frequency differences between test and production
- Async operation timing in real device environments  
- UI update synchronization issues
- Race conditions in the queue processing logic

📊 CURRENT DATABASE IMPLEMENTATION ANALYSIS:
    
    ⏰ SAVE INTERVALS & TRIGGERS:
        • Timer-based auto-save: Every 30 seconds (active app)
        • Background auto-save: Every 2 minutes (when app paused)
        • Transaction-based saves: After each major action
          - Buy materials → immediate save
          - Start production → immediate save  
          - Start shipping → immediate save
        • Lifecycle saves: When app goes to background/foreground
        • Manual save: User-triggered via settings screen
        • Final save: On app disposal/shutdown
    
    💾 SAVE MECHANISM (CURRENT ISSUES):
        ❌ FULL TABLE CLEAR + REWRITE: Every save operation clears ALL tables and rewrites everything
        ❌ NO INCREMENTAL SAVES: Even tiny changes trigger complete database rebuild
        ❌ EXCESSIVE WRITE OPERATIONS: 7+ table operations per save
        ❌ NO DIRTY TRACKING: Can't tell what actually changed
        ❌ TRANSACTION OVERHEAD: Complex multi-table transactions for simple updates
        
        Current save operation sequence:
        1. DELETE FROM materials;        -- Clear all materials
        2. INSERT INTO materials...      -- Rewrite all materials
        3. DELETE FROM products;         -- Clear all products  
        4. INSERT INTO products...       -- Rewrite all products
        5. DELETE FROM active_productions; -- Clear productions
        6. INSERT INTO active_productions... -- Rewrite productions
        7. DELETE FROM shipping_order_items; -- Clear shipping items
        8. DELETE FROM active_shipping_orders; -- Clear shipping orders
        9. INSERT INTO active_shipping_orders... -- Rewrite shipping
        10. DELETE FROM shipping_history_items; -- Clear history items
        11. DELETE FROM shipping_history; -- Clear history
        12. INSERT INTO shipping_history... -- Rewrite history (last 100)
    
    🔍 PERFORMANCE IMPACT ANALYSIS:
        • Small money change (buy $1 material) = FULL DATABASE REWRITE
        • 30-second timer = 2 database rewrites per minute minimum
        • Background save = 30 database rewrites per hour when idle
        • Major transaction = Timer save + immediate save = DOUBLE SAVE
        • App lifecycle changes = Additional saves on pause/resume
        
        Estimated write operations:
        - Active gameplay: ~120+ full rewrites per hour
        - Background idle: ~30+ full rewrites per hour
        - Each rewrite: 12+ DELETE/INSERT operations = 1440+ DB operations/hour
    
    🚨 CRITICAL PERFORMANCE ISSUES:
        ❌ WRITE AMPLIFICATION: 1000x more writes than necessary
        ❌ BATTERY DRAIN: Constant disk I/O every 30 seconds
        ❌ STORAGE WEAR: Excessive flash memory writes on mobile devices
        ❌ FRAME DROPS: UI freezes during full save operations
        ❌ STARTUP DELAYS: Complex loading due to normalized schema
        ❌ CORRUPTION RISK: More write operations = higher failure probability
